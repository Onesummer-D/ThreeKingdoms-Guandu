# 受约束史料智能体

`corpus.json` 是项目内可审阅的运行知识包（H01–H15 历史卡与 D01 游戏规则卡，共16张），`grounding.js` 负责短语/中文二字词片段加权检索、相关性门槛、逐句引用及数字/引文检查和无模型回退；`run-evidence.js` 专门对本局真实游戏记录做可溯源复盘，使用 [G01]（非历史史料）。这些词法检索与校验并不是向量语义检索或事实蕴含证明。公网服务如果设置 `OPENAI_API_KEY`，会把检索到的卡片交给云端模型；没有 Key、模型失败或模型漏引证据时，自动返回本地摘要。

## 运行方式

```powershell
$env:OPENAI_API_KEY = "..."
$env:OPENAI_MODEL = "gpt-5.4-mini"
node server.js
```

服务端接口：`POST /api/historian/ask`，请求体为 `{ "question": "...", "context": "...", "history": [{"role":"user","content":"..."},{"role":"assistant","content":"..."}], "run": { "...": "可选的本局结构化战况" } }`。返回 `answer`、`mode`、`retrieved`、实际引用的 `citations` 和 `answerVersion: grounding-v4`。旧版无 history 请求仍然兼容。

历史仅接受最近三组完整 user/assistant 问答，每条最多 1000 字；system 消息、未完成问答与其他字段不进入模型。指代式追问结合最近一组对话检索，新主题单独检索。剧情上下文仅传当前已经显示的文本，不传完整未解锁剧情或本局推测结局。

Unity 的 `HistorianChatUI` 负责透明图标、半透明悬浮窗、自由输入、来源展开和本局记录。发给后端的 `run` 是已发生数据的精简结构，仅包含资源起终快照、最多40条实际选择及其前后快照、最多12项小游戏结果以及**已抵达**的结局评价；不发送玩家昵称、参谋身份或未解锁节点。未达到结局时不会发出任何终局字段。PNG 与知识包位于 `Assets/Resources/Historian`，知识包须与服务端 `corpus.json` 同步。断网时客户端读取这份包；模型失败时服务器也可返回摘录。摘录不是新的模型回答。

验证命令：`node server/historian-ai/run-eval.js`（固定史料题），`node server/historian-ai/chat-test.js`（历史、真实 HTTP 合约、错误引用和模型故障），`node server/public-advisor/integration-test.js`（公网会话回归和模型超时）。

## 语义意图路由（PR #25 升级）

- 已有 `OPENAI_API_KEY` 和 OpenAI 兼容接口时，`semantic-router.js` 让模型按上下文理解玩家的自由问题，且**只接收严格 JSON 的 `run / history / mixed / unrelated` 意图与 `ending / choices / resources / miniGames / overview` 关注点**。这是 LLM 语义分类，不是向量检索或重新训练模型。
- 流程：明确的本局提问先走安全快速路径；含本局数据或问题含糊时，语义分类优先于普通史料检索；`run` 仅引用 [G01] 玩家已发生记录，`history` 仅检索并校验 Hxx/D01，`mixed` 分别列出游戏与史料两类依据。不能用史书记载代替玩家的失败原因。
- 模型判断「关注点」后由确定性代码从真实记录挑选并排列事实。**模型不得自由编造玩家行动、资源数值、IF 结局或尚未解锁事件**。因此本局回答的措辞尚不是完全自由生成，但比先前不论问题都显示完整固定复盘更聚焦。
- 语义判断请求限定为 160 token、最多 2.2 秒，异常或模型不可用时回退到保守的本局规则/史料检索；无有效本局记录必须返回 `run_unavailable`，不会从史料猜测玩家胜败。实际模型生成历史回答依旧执行逐句引用、数字和引文检查（并非严格事实蕴含证明）。
- 模型分类多一次接口调用，可能增加延迟和少量 token 费用；当前只在有实际本局记录、已显示的游戏上下文或最近对话时启用；空上下文的无关请求不会额外消耗一次模型分类，以减少普通独立史料问答的额外开销。部署需要同步 `grounding.js`、`run-evidence.js`、新文件 `semantic-router.js`（同目录）并重启 8080 后端；Unity 离线识别修复还需重新 Build WebGL。
- 模拟 DeepSeek 由本地 HTTP 模型替身测试覆盖；**真实线上 DeepSeek 与完整 Unity WebGL 仍需单独验收**，尤其要测试「为什么这一轮会输」「刚刚那个决定是不是把战局搞砸了」「袁绍为什么输掉官渡之战」和混合问法。

## 微调边界

当前先用检索增强和引用校验交付。只有在收集到足量、已审阅的问答对，有可用 GPU、模型许可证和独立评测集时，才考虑 LoRA/指令微调。训练集不能把游戏 IF 分支标成史实，也不能把模型自由生成当作史料。没有这些条件时，保持基础模型 + 本地知识包更稳。模型名通过 `OPENAI_MODEL` 配置，默认值是 `gpt-5.4-mini`，部署前应按账号可用模型和官方文档确认。

`eval.jsonl` 目前有16道检索评测，`chat-test.js` 另验证非法引用、断网回退、G01战局复盘和模拟DeepSeek请求格式。

## v4 史料、示范问答和部署边界

- **历史问答 [Hxx]**：H01–H10 是新交稿的谨慎摘编；H11 保留地理知识，H12–H15 来自校订稿附录。检索最多4张史料卡，校验逐句引用、局部词组、数字和原文引语。校验不能代替人工史实核验。
- **本局回顾 [G01]**：请求“我为什么会输”“本局怎么选择的”等问题时，直接使用实际已发生的游戏记录生成确定性说明；只有通关后才说明结局。结局“原因”是游戏自身的设计评价，不能证明现实历史因果，也不推演玩家未游玩的分支。无记录时明确拒绝。
- **文案组10条示范问答**：已置入 `style-examples.json`，仅用于表达风格，不是史料，也不能自动获得引用。
- **设计证据[D01]与本局证据[G01]**：D01只说明游戏四资源/IF；G01只说明玩家本局实际记录。H10关于许攸后事仅玩家明确追问时检索。
- **无外部依赖**：仍是词法匹配，不需要新数据库或 Embedding API；新增史料时必须同步服务端与Unity `corpus.json`。
- 本次仅修改仓库源代码，**不会自动更新运行中的公网服务器**。部署后核验响应的 `answerVersion=grounding-v4`；服务器的实际模型由 `OPENAI_MODEL` 和 `OPENAI_API_URL` 环境变量决定。
